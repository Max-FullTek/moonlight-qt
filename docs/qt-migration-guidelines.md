# Qt 移除與 Rust／GPUI 遷移開發準則

本文記錄 Qt 遷移已確認的需求邊界及工程決策規則，不是整體開發計畫（SD），也不取代個別 Work。實作以 repository 現況與當次 Work 為準；尚未確認的設計不得視為已授權實作。

## 已確認的 SA 決定

- 首階段完成目前 **Windows Lite** 的無 Qt 建置與執行。其他平台及功能另立 Work；首階段完成不代表整個 repository 已移除 Qt。
- 內部實作可依 Rust／GPUI 與既有 C／C++ 的特性改善，不要求逐行翻譯或複製 Qt 的類別、signals/slots、執行緒與視窗結構。
- 改變可見操作流程、功能、相容性，或引入明顯效能取捨前，先提出方案，經 SA 確認後再實作。
- 可接受新的設定格式與重新配對，不把沿用舊設定及配對身分列為首階段必備驗收條件。這不授權刪除或覆寫舊設定、憑證與金鑰；新舊資料應隔離，實際路徑與格式在相關 Work 中確立。

Windows Lite 的功能基準以現有實作、封裝腳本及後續範圍盤點共同確認，不能只依 README 的全產品功能列表。現有封裝入口為 `scripts/build-portable-x64.ps1`；目前保留文字／圖片剪貼簿，麥克風停用，USB/IP、檔案映射及更新器等不屬於目前 Lite 交付功能。停用不等於已解除建置或執行依賴，仍需逐項盤點。

## 遷移原則

1. **保留需求目的，重新評估實作手段。** Qt 寫法不是需求；先釐清使用者需要的結果、舊方法解決的問題及平台限制，再選擇新實作。
2. **移除 Qt 不等於全面改寫成 Rust。** 已穩定的 C 協定庫、C++ 解碼／渲染／輸入邏輯優先沿用；為解除依賴所需的局部調整可在 Work 內進行。大規模重寫與跨模組職責搬移需另行確認。
3. **採用自然的實作，不模擬整套 Qt。** 不為形式一致而建立通用 QObject、signals/slots 或 Qt 型別相容層。過渡 adapter 必須有明確用途、範圍及退出條件。
4. **不順便修正產品行為。** 舊行為看似不佳時，記錄問題與證據；若改善會改變流程、功能或相容性，先做 SA 決策。明確且低風險、屬於當次 Work 的內部缺陷可直接修正並報告。
5. **分段交付。** 每個 Work 應有可驗收結果、依賴、非破壞條件及必要驗證；過渡期可保留 Qt，但必須如實說明剩餘依賴。
6. **不把繞路藏進程式。** 若需要重複狀態、額外程序／執行緒、頻繁複製影音資料、持續輪詢或長期雙重實作，先檢查是否源自可移除的舊設計限制。

## 工程自主權與 SA 確認界線

| 情境 | 處理方式 |
|---|---|
| 更換 Qt 容器、字串、計時器或局部演算法，外部行為與 Work 邊界不變 | Local Agent 自行決定，依需要驗證 |
| repository 證據否定非固定的建議修改點，但需求與驗收不變 | 修正實作假設並繼續，完成時說明 |
| Rust／GPUI 沒有一對一 API，但可用不同內部方法達成相同行為且無重大取捨 | 自行選擇合適方法，不因 API 不同就停工 |
| 需要改動操作順序、快捷鍵、輸入擷取、視窗焦點、錯誤處理或功能語意 | 提出方案，先做 SA 確認 |
| 建議刪除／降低功能、縮小平台支援或改變主機協定相容性 | 提出方案，先做 SA 確認 |
| 改變程序邊界、Rust／C++ 職責、公開 IPC／FFI 契約，或大規模重寫穩定模組 | 若當次 Work 未明確授權，先確認架構與契約 |
| 新增重要依賴、改變授權／部署要求，或更改配對、TLS、憑證信任模型 | 提出影響與替代方案，先確認 |
| 相同行為需要明顯增加延遲、CPU／GPU、記憶體、資料複製或維護複雜度 | 先提供證據及替代方案，確認可接受的取捨 |
| 驗證失敗原因不明、修復風險或範圍擴大 | 停止受影響工作，按既有 Work 規則回報；不自行擴大修復 |

只有受決策影響的部分暫停；不依賴該決定且已授權的工作可繼續。已確認決策不反覆詢問，除非新證據改變其前提。不能用「Rust 比較好」或「原本寫法很差」代替具體證據。

## 遇到不適合直接移植的做法

向 SA 提交以下內容，讓決策可以直接落實：

1. 原本要滿足的需求、現有行為與實作位置；區分必要行為與歷史 workaround。
2. 新環境的具體限制，並說明是已由原始碼／小型驗證確認，還是待查假設。
3. 最少兩個合理方案：維持行為的作法，以及重新設計的作法；若只有一個可行方案，說明原因。
4. 各方案對使用者流程、相容性、效能、平台、依賴、維護成本及其他 Work 的影響。
5. 建議方案、需要確認的單一取捨、驗收方式與切換／回復方式。

例如浮動選單若在 GPUI 下無法直接重現，應比較其他視窗／繪製方式及其焦點、全螢幕、DPI、HDR 與輸入擷取影響。不能直接移除選單，也不能為複製外觀而默默接受串流延遲或焦點退化。

## 每個實作 Work 的必要內容

- 目標、範圍、不包含項目、依賴及已固定的技術決策。
- 保留的功能／行為、允許的變更與已確認 SA 決策。
- 每項 Task 的驗收條件，以及相應的自動化或人工驗證。
- 過渡期仍需 Qt 的模組、移除條件與既有可用路徑。
- 涉及效能取捨時，在修改前確立比較情境與可接受標準；未量測不得宣稱效能等同。

測試依 Work 和實際風險選擇，不擴大為無關 QA。協定、配對及生命週期採有意義的契約／整合驗證；視窗、輸入、剪貼簿與真實串流行為依 Work 明列實機驗收。必要條件未驗證，不能報 complete。

## 首階段「不需要 Qt」的交付定義

- Windows Lite 正式交付路徑可在沒有 Qt SDK／工具的乾淨建置環境完成，不使用 qmake、moc、QML 工具或 windeployqt。
- 前端、worker、helper 及實際載入的第三方元件均不依賴 Qt；同時檢查靜態連結、直接／間接 DLL 及動態外掛載入，不能只看封裝內是否有 Qt DLL。
- 封裝在未安裝 Qt、未借用開發機 Qt PATH 的環境執行，通過已確認功能範圍的驗收。
- 已遷移測試可脫離 Qt 執行；舊產品的 Qt 測試或 CI 若仍保留，必須標明其歸屬，不作為 Lite 的建置前提。
- 其他平台與舊功能的 Qt 原始碼可在首階段保留，不能因此宣稱全專案無 Qt。

## 後續仍需確立的設計

以下不是已確認結論，應在相應 Work 開始前提出具體方案：

- Rust 與 C++ 的長期職責、worker 程序邊界，以及 IPC 或 FFI 的選擇。
- 無 Qt 建置入口、工具鏈與舊建置的過渡方式。現有架構文件的 qmake 預設仍適用舊路徑；新路徑的例外需在建置 Work 中確立。
- 浮動介面、視窗與顯示服務的實作歸屬及允許的體驗差異。
- 新設定／配對資料的存放方式與舊版並存策略。
- 各項高風險行為與效能比較的具體驗收情境。

不需一次決定所有函式庫或細節；只有會影響產品、架構、相容性或跨 Work 邊界的決策才回到 SA。
